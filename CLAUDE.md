## Commands

This project uses [`uv`](https://github.com/astral-sh/uv) — not `pip` or `poetry`.

```bash
# Start dev server with hot-reload
uv run uvicorn main:app --reload

# Run all tests
uv run pytest

# Run only unit tests (no network)
uv run pytest -m "not system"

# Run only system tests (hit live GRT API)
uv run pytest -m system

# Run a single test
uv run pytest test_main.py::test_read_vehicle_unit -v

# Export OpenAPI schema, then lint against Microsoft Azure API Style Guidelines
uv run python export_openapi.py
docker run --rm -v "$(pwd):/work" -w /work stoplight/spectral lint openapi.json
```

## Architecture

Single-file FastAPI app (`main.py`) that acts as a translation layer between GTFS-Realtime protobuf feeds from multiple transit agencies and clean JSON REST responses modeled on Microsoft Graph API conventions.

**Data flow**: upstream protobuf API → deserialize via `gtfs_realtime_pb2` → flatten/clean → cache → serve JSON

**Multi-agency dispatch**: The `Host` header is matched against per-agency regex patterns (`TRANSIT_GRT_HOST_REGEX`, etc.) to select an `AgencyState`. Unknown hosts fall back to GRT. Each agency has isolated caches, stop data, and a route map.

**Agency model**:
- `AgencyConfig` — feed URLs, auth headers, SSL config, whether route→feed-key discovery is needed
- `AgencyState` — per-agency mutable state (vehicles/trips/alerts caches, stops, route map)
- GRT uses two feed keys (`bus`/`rail`) and dynamically discovers which routes map to which feed. TTC and OCTranspo use a single `all` feed key.

**Caching**: Each feed type is cached per feed-key within each agency's state. TTL is configurable via `CACHE_TTL_SECONDS` env var (default 2s). Static GTFS stops are cached with ETag/Last-Modified and refreshed every 10 minutes.

**Background loops** (one pair per agency, started in `lifespan`):
- `update_route_map_loop()` — refreshes route→feed-key mapping every 60s (GRT only; skipped for single-feed agencies)
- `update_static_data_loop()` — refreshes GTFS stops zip every 10 minutes

**Endpoints** (all list responses wrap results in `{"value": [...]}` per Graph API convention):
- `GET /routes/{route_id}/vehicles` — live vehicle positions filtered by route
- `GET /routes/{route_id}/trips` — GTFS-RT trip updates for a route
- `GET /alerts` — all active service alerts
- `GET /routes/{route_id}/alerts` — alerts filtered by route
- `GET /stations` — static stop metadata from GTFS zip
- `GET /stations/{station_id}` — single stop by ID

**Testing pattern**: Unit tests mock the upstream protobuf feed with `@patch` and pre-populate `_DEFAULT_AGENCY` state directly (caches, stops, route map). The `clear_caches` fixture resets `_DEFAULT_AGENCY` state before each test. System tests (marked `@pytest.mark.system`) hit the live GRT API via the lifespan.

**OpenAPI schema** is auto-generated by FastAPI and exported to `openapi.json` via `export_openapi.py`. The `.spectral.yaml` config lints this against `spectral:oas` extended with Azure API style rules.

## Versioning

App version lives in `pyproject.toml` (`[project].version`). `chart/Chart.yaml` has two independent version fields:

- `appVersion` — the app version this chart deploys. Keep in sync with `pyproject.toml` when building a new image.
- `version` — the chart's own version. Only bump when the chart itself changes (templates, values schema, etc.). It does **not** need to match `appVersion`.

Version bump policy:
- **patch** (`x.y.Z`): bugfixes where the old version should never be used (critical hotfixes targeting a specific minor)
- **minor** (`x.Y.0`): everything else — features, refactors, and most bugfixes. This preserves the option to hotfix an earlier minor version later.
- **major** (`X.0.0`): breaking API changes

## Deployment

Deployed to a k3s cluster at `ubuntu.jskw.dev`. There is no container registry — images are built locally and loaded directly into containerd.

Images are tagged with the app version from `pyproject.toml`. Passing a new tag to `helm upgrade` changes the image reference in the Deployment, which triggers a rolling update automatically — no `kubectl rollout restart` needed.

```bash
# Read version from pyproject.toml
VERSION=$(grep '^version' pyproject.toml | awk -F'"' '{print $2}' | tee /dev/stderr)

# 1. Build for amd64 (k3s node architecture)
docker buildx build --platform linux/amd64 -t grt-times:$VERSION .

# 2. Save image to a tar in the workspace (never write to /tmp on the host)
docker save grt-times:$VERSION -o grt-times.tar

# 3. Copy to server and import into k3s containerd namespace
#    Must complete before helm upgrade — the rolling update starts immediately on upgrade.
rsync -az grt-times.tar ubuntu.jskw.dev:/tmp/
ssh ubuntu.jskw.dev "sudo ctr --namespace k8s.io images import /tmp/grt-times.tar"

# 4. Deploy — new image tag triggers rolling update; no restart needed
helm upgrade grt-times ./chart \
  --set image.tag=$VERSION \
  --set 'envFrom[0].secretRef.name=transit-api-secrets' \
  --set 'env[0].name=UVICORN_FORWARDED_ALLOW_IPS' \
  --set 'env[0].value=10.42.0.0/16' \
  --set 'env[1].name=SUPPRESS_HEALTHCHECK_LOG_SUBNET' \
  --set 'env[1].value=10.42.0.0/16'
```

The Helm chart is in `chart/`. API keys are kept out of the chart via a Kubernetes Secret.

To install from scratch:

```bash
# 1. Create the secret (once; never commit key values)
ssh ubuntu.jskw.dev "sudo kubectl create secret generic transit-api-secrets \
  --from-literal=TRANSIT_TTC_API_KEY=xxx \
  --from-literal=TRANSIT_OCT_API_KEY=xxx"

# 2. Install the chart referencing the secret
VERSION=$(grep '^version' pyproject.toml | awk -F'"' '{print $2}')
helm install grt-times ./chart \
  --set image.tag=$VERSION \
  --set 'envFrom[0].secretRef.name=transit-api-secrets' \
  --set 'env[0].name=UVICORN_FORWARDED_ALLOW_IPS' \
  --set 'env[0].value=10.42.0.0/16' \
  --set 'env[1].name=SUPPRESS_HEALTHCHECK_LOG_SUBNET' \
  --set 'env[1].value=10.42.0.0/16'
```


## Operational Safety

- **No Unauthorized Deletions**: Never delete files on the local machine or remote servers (especially logs, tarballs, or backups) without explicit user approval.
- **No Unauthorized Restarts**: Never restart system services (e.g., `k3s`, `containerd`, `docker`) without explicit user approval.
- **Kubeconfig**: Always use the local `helm` and `kubectl` with the appropriate `KUBECONFIG` (e.g., `~/.kube/ubuntu.yaml` for the production cluster). Do not run cluster commands via SSH.
- **Resource Pressure**: If deployment fails due to disk pressure or other resource constraints, report the specific error and available capacity to the user rather than attempting to self-remediate by clearing space.
